# 广播分配 ID 方案

> 状态：方案已讨论确定，待实现
> 日期：2026-09-11
> 适用：Modbus RTU 多从机总线（10~30 台）

## 1. 需求背景

- 多台从机挂同一条 RS485 母线，母线上只有一台主设备。
- 从机出厂默认 `node_id = 1`，多台同上必然 ID 冲突。
- 客户需求：
  1. 广播一条报文，总线上**所有从机**（含已分配 ID 的）上报自己的 UID + 当前 ID，客户获得全网设备清单；
  2. 客户**自行**决定每个 UID 分配什么 ID，从机通过 UID 识别"这条改 ID 指令是发给本机的"。

## 2. 为什么不做"自动分配 ID"

Modbus RTU 是主从架构，**从机之间没有通信路径**：从机 A 拿到 ID=2 后无法告知从机 B"2 已被占用"。自动互分配需要从机间协调协议（令牌等），复杂度高且与"客户自行分配"的需求冲突。故放弃。

核心原则：**主机是唯一协调者，UID 是设备唯一身份**。所有"点对点"语义都用 UID 寻址实现，绕开"所有未分配设备都是 ID=1 无法单播"的死结。

## 3. 协议总览（三阶段）

```
┌──────────┐ ①收集广播      ┌──────────┐
│  主机    │ ──────────────→│ 所有从机 │
│          │                │          │
│          │ ①分时上报 UID  │  hash(UQID,round) % 128
│          │ ←──────────────│  每台延时 slot×50ms 发帧
│          │  (撞车→CRC丢弃→下轮换盐重来)
│          │
│          │ ②逐台绑定广播   (UID+新ID, 0x43)
│          │ ←─ 新ID地址回0x45应答回显UID（UID匹配者）
│          │
│          │ ③广播UID查ID验证 (0x44)
└──────────┘
```

### ① 清点阶段（收集 UID）

- 主机广播收集命令，**两种模式**（value 高字节）：mode=0x00 仅 ID=1（未分配）设备回复，用于首次分配；mode=0x01 所有从机回复（含已分配），用于全网盘点、查 ID 占用/冲突。
- 参与的从机计算 `slot = hash(UQID, round) % 128`，收到广播后延时 `slot × 50ms` 发上报帧。
- 撞车（两台同 slot）→ 总线电平冲突 → 主机 CRC 校验失败丢弃 → 这两台本轮没报上。
- 主机每轮结束换 round 重播，直到"连续 1~2 轮无新 UID"或达轮数上限。
- 收敛统计（30 台 / 128 slot）：

| 轮次 | 剩余未收集 | 本轮期望成功 | 剩余 |
|------|-----------|-------------|------|
| 1 | 30 | ~24 | ~6 |
| 2 | ~6 | ~5 | ~1 |
| 3 | ~1 | ~1 | ~0 |

2 轮基本收齐，协议封顶 6 轮（9600bps 下约 40 秒）。

- 该阶段价值：全网设备清单（UID ↔ 当前 ID）、发现 ID 冲突、掉线审计、可重复跑做资产盘点；**对 ID 已经全乱的总线也自愈**（分时上报不依赖 ID）。

### ② 分配阶段（UID 寻址绑定）

- 主机逐台广播绑定帧（携带 UID + 新 ID）。
- 所有从机都收到，但**只有 UID 匹配者执行**：写 node_id → Param_Save 存 Flash → 以**新 ID** 回 0x43 应答（回显 UID）；不匹配者（含其他已分配设备）静默。
- 首次分配和修改已有 ID 走**同一条指令**。

### ③ 验证阶段

- 主机广播 0x44 查询帧（携带 UID），UID 匹配者以**当前 ID** 应答（回显 UID）。
- 主机将应答 ID 与清点清单中该 UID 的分配目标比对，一致即绑定成功；失败重试，全部通过后按 ID 轮询点名收尾。
- 按 UID 查 ID **免疫 ID 冲突**：筛选条件是 UID（全球唯一），总线上有且仅有一台应答；旧方案"按 ID 读 UID 寄存器"在 ID 冲突时两台同时应答会失败。

## 4. slot 哈希分时机制详解

### 4.1 slot 是什么

把广播后 128 × 50ms = 6.4s 的时间窗切成 128 个时隙，每台设备按 UID"抽签"占一个时隙，只在自己的时隙到点时发帧。抽签 = 哈希：

```
/* MurmurHash3 finalizer 风格雪崩混合，round 为轮次号 */
h  = UQID0 ^ (UQID1 * 0x9E3779B9) ^ (UQID2 * 0x85EBCA6B) ^ (round * 0xC2B2AE35);
h ^= h >> 16;  h *= 0x7FEB352D;  h ^= h >> 15;
h *= 0x846CA68B;  h ^= h >> 16;
slot = h % 128;          /* 0~127 */
delay  = slot * 50ms;    /* 自收到广播起计 */
```

- 50ms = 17 字节上报帧 @9600bps 传输时间（约 17.7ms）+ 3.5 字符帧定界静默（约 4ms，主机判帧结束所需）+ 充分保护余量。曾评估 25ms 槽：相邻槽间隔仅 7.3ms，扣除 4ms 帧定界静默后裕量只剩 ~3.3ms，从机延时起点的判定偏差/时钟偏差即可击穿，导致相邻帧被主机粘连而 CRC 全弃——故改为 50ms（裕量 ~28ms）。
- 雪崩哈希保证：UID 差 1，输出面目全非且均匀分布 → 同批次流水号连续的芯片也均匀散开。

### 4.2 关键认知：哈希不保证 slot 互不相同

slot 本质是"30 人抽 128 个签"，**撞号是允许发生的**：

- 撞了 → 两帧同时驱动总线 → 主机收到乱码 → CRC 丢弃 → 两台本轮白报；
- 从机不知道自己撞了（半双工发帧时听不到总线），也无需知道；
- 主机无需知道谁撞了，只看每轮收到哪些 UID。

**round 参与哈希 = 每轮重新洗牌**：这轮撞了，下轮两台的 slot 全变，撞的概率回到独立的 1/128。连续撞 k 轮概率 = (1/128)^k（2 轮 1/16384，3 轮 1/200 万）。"一直撞"仅在两台 UID 完全相同（物理不可能）或哈希缺陷（round 参与 XOR/乘法，不会）时发生。

一句话：**放弃分时准确性，用多轮换盐收敛时域**（ALOHA 思想）。

### 4.3 为什么不用更大 slot 数

1024 slot 可让 30 台单轮几乎全成，但一轮 51.2s，比多轮 128 slot 慢得多。撞车是这类协议的正常运行方式，128 slot 是"单轮短"与"多轮收敛快"的平衡点。

## 5. 哈希 vs 真随机数（TRNG）决策

**结论：用 UID 哈希，不用 TRNG。**

哈希是确定性函数（同 UID+round 永远同 slot），不是随机数；但雪崩哈希取模后均匀性等效于抽签，与真随机不可区分。真随机在此场景反而有缺点：

| | UID 哈希 | TRNG 真随机 |
|---|---|---|
| 不同设备的"种子" | **物理保证不同**（96 位 UID 出厂固化，全球唯一） | 统计保证不同（有极小概率重复） |
| 可调试性 | 主机/从机可复算同一张 slot 表，测试工具可预测每台出现时刻 | 完全不可复现，难排查 |
| 故障模式 | 无 | TRNG 初始化时序错误/故障时可能输出退化（如全 0）→ 所有设备抽到同一数 → 必然全撞，比哈希更差 |
| 实现成本 | 十几行整数运算 | 需 TRNG 初始化与就绪等待 |

预留升级路径：若将来担心同批次 UID 分布有规律，可让主机每轮用 TRNG 生成"盐"随广播下发，从机算 `hash(UQID, salt)`——真随机的均匀性 + 主机握盐可复现。30 台规模不需要。

## 6. 报文协议（完整规范 v1.7，私有功能码）

### 6.1 通用约定
- 串口 8N1，波特率与常规通信一致（默认 9600bps）；CRC16-Modbus（多项式 0xA001，初值 0xFFFF），**低字节在前**。
- **UID 全部小端**：每个 32 位字（UQID0/UQID1/UQID2）低字节在前发送，字顺序仍 UQID0→UQID1→UQID2。**ID 线上一律 1 字节**（Modbus 地址本就 1 字节，1~247）：从机回复首字节 = 发帧时的当前 ID；绑定命令中新 ID 亦为 1 字节。
- 帧间静默 ≥3.5 字符（9600bps 下约 4ms）。
- **功能码全私有化，方向即编码**（Modbus 规范用户自定义区 65~72，即 0x41~0x48）：主机→总线 **0x41 收集 / 0x43 绑定 / 0x44 查询**；从机→主机 **0x42 上报 / 0x45 绑定应答 / 0x46 查询应答**——两集合零交集，从机发出的帧在 func 层就不可能被当成主机命令。私有帧沿用标准"功能码+寄存器地址"习惯——0x41 @0x2713（保留地址转正为分配协议命令寄存器），0x43 绑定 / 0x44 查询 @0x2710（ID 寄存器，被修改/被查询对象）。

### 6.2 报文总览

| 序号 | 报文 | 方向 | 功能码 | 帧长 |
|---|---|---|---|---|
| ① | 收集命令（广播，两种模式） | 主机 → 总线 | 0x41 | 8 字节 |
| ② | UID 上报（当前 ID + UID） | 从机 → 主机 | 0x42 | 17 字节 |
| ③ | ID 绑定命令（广播） | 主机 → 总线 | 0x43 | 19 字节 |
| ④ | 绑定应答 | 从机 → 主机 | 0x45 | 18 字节 |
| ⑤ | UID 查询命令（广播） | 主机 → 总线 | 0x44 | 18 字节 |
| ⑥ | 查询应答 | 从机 → 主机 | 0x46 | 18 字节 |

私有帧沿用标准"功能码+寄存器地址"习惯：0x41 指向分配协议命令寄存器 0x2713（保留地址转正），0x43/0x44 指向 ID 寄存器 0x2710（被修改/被查询对象）；从机按 addr=0 + func + 地址三重匹配过滤。

示例约定：统一假设 UID=11223344-55667788-99AABBCC，当前 ID=1，新 ID=5；小端 UID 字节序即 `44 33 22 11 88 77 66 55 CC BB AA 99`；示例帧 CRC 以 `[crc_L][crc_H]` 占位。

### 6.3 ① 收集命令（主机 → 总线，广播，0x41 @0x2713，共 8 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 0x00 | 广播地址 |
| 1 | 0x41 | 收集命令 |
| 2~3 | 0x27 0x13 | 分配协议命令寄存器 0x2713（保留地址转正） |
| 4 | mode | 0x00=仅 ID=1（未分配）设备回复；0x01=所有设备回复 |
| 5 | round | 轮次号 0~255 循环 |
| 6~7 | CRC16 | 低字节在前 |

mode=0x00 用于首次分配清点（只有出厂态设备参与）；mode=0x01 用于全网盘点（含已分配设备，查 ID 占用/冲突）。

示例（round=0）：A（仅未分配）`00 41 27 13 00 00 [crc_L][crc_H]`；B（全员）`00 41 27 13 01 00 [crc_L][crc_H]`

从机不立即应答；应在 slot 到点后发 ② 帧。

### 6.4 ② UID 上报帧（从机 → 主机，分时主动发，0x42，共 17 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 当前ID | **首字节 = 本机当前 ID**（mode=0 时未分配设备即 0x01），与常规应答形态一致；主机按私有功能码 0x42 识别协议帧 |
| 1 | 0x42 | UID 上报 |
| 2 | 0x0C | byteCount=12 |
| 3~6 | UQID0 | 4 字节小端 |
| 7~10 | UQID1 | 4 字节小端 |
| 11~14 | UQID2 | 4 字节小端 |
| 15~16 | CRC16 | 低字节在前 |

示例（UID=11223344-55667788-99AABBCC，当前 ID=1）：
`01 42 0C 44 33 22 11 88 77 66 55 CC BB AA 99 [crc_L][crc_H]`

从机延时 = `hash(UQID, round) % 128` × 50ms（自收到①帧的 3.5 字符静默结束起计）。撞车帧叠加乱码，主机 CRC 丢弃。

### 6.5 ③ 绑定命令（主机 → 总线，广播，0x43 @0x2710，共 19 字节）

语义：**UID 是筛选条件，不是写入数据**——UID 匹配者把自己的 node_id（0x2710）改成新 ID。

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 0x00 | 广播地址 |
| 1 | 0x43 | 绑定命令 |
| 2~3 | 0x27 0x10 | ID 寄存器（本命令的操作对象） |
| 4~15 | UID(12B) | UQID0/UQID1/UQID2 各 4 字节小端 |
| 16 | 新ID | 1 字节（1~247） |
| 17~18 | CRC16 | 低字节在前 |

示例（给 UID=11223344-55667788-99AABBCC 分配 ID=5）：
`00 43 27 10 44 33 22 11 88 77 66 55 CC BB AA 99 05 [crc_L][crc_H]`

识别：addr=0 + func=0x43 + 地址=0x2710 → switch(func) 加 case 走分配专用分支，不进入常规 Param_WriteByReg。UID 匹配者执行写入；不匹配者（含其他已分配设备）静默。与常规单播 0x06@0x2710 改 ID 并存不冲突（后者针对已知地址设备）。

### 6.6 ④ 绑定应答（从机 → 主机，以新 ID 发，0x45，共 18 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 新ID | **应答地址 = 刚分配的新 ID**（写入值由此确认） |
| 1 | 0x45 | 应答功能码（区别于命令 0x43，防从机把应答误当命令） |
| 2~3 | 0x27 0x10 | 地址回显 |
| 4~15 | UID(12B) | 回显本机 UID（小端），证明哪台设备确认 |
| 16~17 | CRC16 | 低字节在前 |

示例（新 ID=5）：`05 45 27 10 44 33 22 11 88 77 66 55 CC BB AA 99 [crc_L][crc_H]`

（应答码不回显命令码：从机帧 func 永不落入主机命令集合，"应答被当命令"结构上不可能。）

时序：从机写 node_id → Param_Save（Flash 几十 ms）→ 发应答；主机应答超时 ≥300ms。

### 6.7 ⑤ UID 查询命令（主机 → 总线，广播，0x44 @0x2710，共 18 字节）

语义：**UID 是筛选条件**——总线上只有 UID 匹配的那一台设备应答（见 6.8）。用于绑定后验证，也兼做日常"按 UID 查当前 ID"。

帧格式：

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 0x00 | 广播地址 |
| 1 | 0x44 | UID 查询 |
| 2~3 | 0x27 0x10 | ID 寄存器（被查询对象） |
| 4~15 | UID(12B) | UQID0/UQID1/UQID2 各 4 字节小端 |
| 16~17 | CRC16 | 低字节在前 |

示例（查询 UID=11223344-55667788-99AABBCC）：
`00 44 27 10 44 33 22 11 88 77 66 55 CC BB AA 99 [crc_L][crc_H]`

识别：addr=0 + func=0x44 + 地址=0x2710，与 0x43 共用 UID 比对逻辑；不匹配者（含其他所有设备）静默。应答超时建议 ≥100ms，超时可重发，重复执行无副作用。

为何改按 UID 查 ID（替代旧"按新 ID 读 UID 寄存器 0x03"）：

- 旧方式按 ID 单播：若总线上存在 ID 冲突（两台同 ID），两台同时应答互相干扰，验证不可靠；
- 新方式筛选条件是 UID（全球唯一），**免疫 ID 冲突**，且与绑定阶段的寻址逻辑一致（都是 UID）；
- UID 寄存器 0x2741~0x2746 保留（调试/上位机读 UID 用），不再是验证必经路径。

### 6.8 ⑥ 查询应答（从机 → 主机，以当前 ID 发，0x46，共 18 字节）

帧格式：

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 当前ID | **应答地址 = 本机当前 ID** |
| 1 | 0x46 | 应答功能码（区别于命令 0x44，防从机把应答误当命令） |
| 2~3 | 0x27 0x10 | 地址回显 |
| 4~15 | UID(12B) | 回显本机 UID（小端），证明哪台设备应答 |
| 16~17 | CRC16 | 低字节在前 |

示例（该设备当前 ID=5）：`05 46 27 10 44 33 22 11 88 77 66 55 CC BB AA 99 [crc_L][crc_H]`

验证逻辑：主机将应答中的当前 ID 与清点清单中该 UID 的分配目标比对，一致即绑定成功。

### 6.9 流程级时序

- ① 广播后主机静默收听 128 × 50ms = 6.4s（一轮）；每轮结束 round+1 重播，直到连续 1~2 轮无新 UID（封顶 6 轮）。
- ③ 逐台发送，收到 ④（绑定应答）再发下一台；30 台约 10s。
- ⑤⑥ 逐台查询验证：广播 ⑤ 等 ⑥，每台约 50ms，30 台 <2s。
- 清点/分配期间主机暂停常规轮询（心跳等）。

### 6.10 与严格 Modbus RTU 的偏差（需在协议文档中向客户声明）

- 0x41~0x46 属 Modbus 规范用户自定义区（65~72），帧结构与 CRC 计算与标准一致，属合规私有扩展。
- ② 帧是从机**主动上报**（首字节=当前 ID）：标准从机不主动发帧——私有扩展 1。
- ④/⑤ 应答均是对广播命令的应答：标准规定广播不应答；本协议在私有分支内应答（地址=新 ID/当前 ID），不影响常规分支行为——私有扩展 2。

1. **App_Modbus**：switch(func) 新增 case 0x41/0x42/0x43/0x44/0x45/0x46——0x41 广播收集（mode 字节区分仅未分配/全员）、slot 延时定时（可复用 nbDelay）、0x42 上报帧发送（绕过正常应答路径）、0x43 绑定帧处理（UID 比对 + 写 node_id + 以新 ID 回 0x45）、0x44 查询处理（UID 比对 + 以当前 ID 回 0x46，与 0x43 共用 UID 比对逻辑）。**func ∈ 0x40~0x48 中未定义的一律静默忽略、不回异常帧**——否则同 ID 从机听到其他从机的 ②/④/⑤ 帧（首字节恰为本机 ID）会回异常帧污染总线。注意先确认现有广播帧（addr=0）的处理路径（是否直接丢弃）再决定分支挂载点。
2. **App_Params**：Init 时读 96 位 UID（`EFM_GetUID()`，DDL 现成接口，无需解锁/初始化，工程已编译 hc32_ll_efm.o）；新增 0x2741~0x2746 只读寄存器映射。
3. **寄存器总览.md**：新增 0x2741~0x2746 只读寄存器定义；0x2713 由"保留"转正为分配协议命令寄存器（同步更新 App_Params.h 注释）。
4. 主机侧（客户/上位机）按第 6 节报文实现。

## 8. 设计决策记录

| 决策点 | 结论 | 理由 |
|---|---|---|
| 自动分配 ID | 放弃 | 从机间无通信路径，且客户要自行分配 |
| 收集命令 | 私有码 0x41，mode(0x00 仅未分配/0x01 全员)+round | 首次分配只需未分配设备；盘点/审计用全员模式 |
| 上报命令 | 私有码 0x42 | 从机主动发帧，借 0x03 形态名不副实 |
| 绑定命令 | 私有码 0x43 @0x2710（应答 0x45 回显 UID，addr=新ID） | UID 是筛选条件不是写入数据；地址字段指向被修改对象 0x2710，与常规单播 0x06@0x2710 并存不冲突 |
| 地址字段 | 私有帧沿用"功能码+地址"习惯：0x41@0x2713、0x43@0x2710 | 与标准 Modbus 格式习惯统一；从机三重匹配（addr=0+func+地址）防误触发；0x2713 保留地址转正 |
| UID 字节序 | 小端 | 客户要求；CRC 保持小端不变 |
| UID 寄存器 | 0x2741~0x2746 只读，小端映射 | 紧跟故障状态 0x2740；96 位=6×16 位寄存器 |
| slot 来源 | UID 哈希 + round 换盐 | 物理唯一种子、可复现、无故障模式 |
| TRNG | 不用（预留盐升级路径） | 统计保证弱于物理保证；退化输出反而全撞 |
| slot 数 | 128 × 50ms | 30 台 2~3 轮收敛，单轮 6.4s；50ms 保证帧定界静默（3.5 字符≈4ms）裕量充足（25ms 槽裕量仅 ~3.3ms 过紧）。槽宽宜随波特率配置 |
| 回复帧首字节 | 发帧时的当前 ID（1 字节） | 与常规 Modbus 应答形态一致；协议帧靠私有功能码 0x41~0x46 区分 |
| ID 线上宽度 | 一律 1 字节 | Modbus 地址本就 1~247，2 字节冗余；上报帧 19→17B、绑定命令 20→19B |
| 应答码独立 | ④=0x45、⑤=0x46，不回显命令码 | 方向即编码（主机 0x41/0x43/0x44 vs 从机 0x42/0x45/0x46 零交集）；UID 比对对"听到自己应答帧"失效（UID 恰为本机），func 层是防自听回环的第二道独立防线 |
| UID 验证 | 0x44 广播按 UID 查当前 ID | 免疫 ID 冲突：UID 全球唯一，有且仅有一台应答；按 ID 读 UID 寄存器在 ID 冲突时两台同答会失败 |
| UID 寄存器 0x2741~0x2746 | 保留只读，小端映射 | 调试/上位机读 UID 用，不再是验证必经路径 |
