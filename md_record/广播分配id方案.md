# 广播分配 ID 方案

> 状态：方案已讨论确定，待实现
> 日期：2026-09-11
> 适用：Modbus RTU 多从机总线（10~30 台）

## 1. 需求背景

- 多台从机挂同一条 RS485 母线，母线上只有一台主设备。
- 从机出厂默认 `node_id = 1`，多台同上必然 ID 冲突。
- 客户需求：
  1. 广播一条报文，总线上**所有从机**（含已分配 ID 的）上报自己的 UID + 当前 ID，客户获得全网设备清单；
  2. 客户**自行**决定每个 UID 分配什么 ID，从机通过 UID 识别"这条改 ID 指令是发给本机的"。

## 2. 为什么不做"自动分配 ID"

Modbus RTU 是主从架构，**从机之间没有通信路径**：从机 A 拿到 ID=2 后无法告知从机 B"2 已被占用"。自动互分配需要从机间协调协议（令牌等），复杂度高且与"客户自行分配"的需求冲突。故放弃。

核心原则：**主机是唯一协调者，UID 是设备唯一身份**。所有"点对点"语义都用 UID 寻址实现，绕开"所有未分配设备都是 ID=1 无法单播"的死结。

## 3. 协议总览（三阶段）

```
┌──────────┐ ①收集广播      ┌──────────┐
│  主机    │ ──────────────→│ 所有从机 │
│          │                │          │
│          │ ①分时上报 UID  │  hash(UQID,round) % 128
│          │ ←──────────────│  每台延时 slot×25ms 发帧
│          │  (撞车→CRC丢弃→下轮换盐重来)
│          │
│          │ ②逐台绑定广播   (UID+新ID)
│          │ ←─ 新ID回0x10应答（UID匹配者）
│          │
│          │ ③单播回读UID比对 (0x2741~0x2746)
└──────────┘
```

### ① 清点阶段（收集 UID）

- 主机广播收集命令，所有从机参与（**不区分是否已分配 ID**）。
- 每台从机计算 `slot = hash(UQID, round) % 128`，收到广播后延时 `slot × 25ms` 发上报帧。
- 撞车（两台同 slot）→ 总线电平冲突 → 主机 CRC 校验失败丢弃 → 这两台本轮没报上。
- 主机每轮结束换 round 重播，直到"连续 1~2 轮无新 UID"或达轮数上限。
- 收敛统计（30 台 / 128 slot）：

| 轮次 | 剩余未收集 | 本轮期望成功 | 剩余 |
|------|-----------|-------------|------|
| 1 | 30 | ~24 | ~6 |
| 2 | ~6 | ~5 | ~1 |
| 3 | ~1 | ~1 | ~0 |

2 轮基本收齐，协议封顶 6 轮（9600bps 下约 20 秒）。

- 该阶段价值：全网设备清单（UID ↔ 当前 ID）、发现 ID 冲突、掉线审计、可重复跑做资产盘点；**对 ID 已经全乱的总线也自愈**（分时上报不依赖 ID）。

### ② 分配阶段（UID 寻址绑定）

- 主机逐台广播绑定帧（携带 UID + 新 ID）。
- 所有从机都收到，但**只有 UID 匹配者执行**：写 node_id → Param_Save 存 Flash → 以**新 ID** 回标准 0x10 应答；不匹配者（含其他已分配设备）静默。
- 首次分配和修改已有 ID 走**同一条指令**。

### ③ 验证阶段

- 主机用新 ID 单播读 UID 寄存器（0x2741~0x2746），回读比对。
- 失败重试；全部通过后按 ID 轮询点名收尾。
- 回读 UID 比"回读 node_id"更强：防止 ID 写歪但碰巧读回一致。

## 4. slot 哈希分时机制详解

### 4.1 slot 是什么

把广播后 128 × 25ms = 3.2s 的时间窗切成 128 个时隙，每台设备按 UID"抽签"占一个时隙，只在自己的时隙到点时发帧。抽签 = 哈希：

```
/* MurmurHash3 finalizer 风格雪崩混合，round 为轮次号 */
h  = UQID0 ^ (UQID1 * 0x9E3779B9) ^ (UQID2 * 0x85EBCA6B) ^ (round * 0xC2B2AE35);
h ^= h >> 16;  h *= 0x7FEB352D;  h ^= h >> 15;
h *= 0x846CA68B;  h ^= h >> 16;
slot = h % 128;          /* 0~127 */
delay  = slot * 25ms;    /* 自收到广播起计 */
```

- 25ms = 21 字节上报帧 @9600bps 传输时间（约 20ms）+ 帧间隔余量，相邻 slot 的帧不会首尾相撞。
- 雪崩哈希保证：UID 差 1，输出面目全非且均匀分布 → 同批次流水号连续的芯片也均匀散开。

### 4.2 关键认知：哈希不保证 slot 互不相同

slot 本质是"30 人抽 128 个签"，**撞号是允许发生的**：

- 撞了 → 两帧同时驱动总线 → 主机收到乱码 → CRC 丢弃 → 两台本轮白报；
- 从机不知道自己撞了（半双工发帧时听不到总线），也无需知道；
- 主机无需知道谁撞了，只看每轮收到哪些 UID。

**round 参与哈希 = 每轮重新洗牌**：这轮撞了，下轮两台的 slot 全变，撞的概率回到独立的 1/128。连续撞 k 轮概率 = (1/128)^k（2 轮 1/16384，3 轮 1/200 万）。"一直撞"仅在两台 UID 完全相同（物理不可能）或哈希缺陷（round 参与 XOR/乘法，不会）时发生。

一句话：**放弃分时准确性，用多轮换盐收敛时域**（ALOHA 思想）。

### 4.3 为什么不用更大 slot 数

1024 slot 可让 30 台单轮几乎全成，但一轮 25.6s，比多轮 128 slot 慢得多。撞车是这类协议的正常运行方式，128 slot 是"单轮短"与"多轮收敛快"的平衡点。

## 5. 哈希 vs 真随机数（TRNG）决策

**结论：用 UID 哈希，不用 TRNG。**

哈希是确定性函数（同 UID+round 永远同 slot），不是随机数；但雪崩哈希取模后均匀性等效于抽签，与真随机不可区分。真随机在此场景反而有缺点：

| | UID 哈希 | TRNG 真随机 |
|---|---|---|
| 不同设备的"种子" | **物理保证不同**（96 位 UID 出厂固化，全球唯一） | 统计保证不同（有极小概率重复） |
| 可调试性 | 主机/从机可复算同一张 slot 表，测试工具可预测每台出现时刻 | 完全不可复现，难排查 |
| 故障模式 | 无 | TRNG 初始化时序错误/故障时可能输出退化（如全 0）→ 所有设备抽到同一数 → 必然全撞，比哈希更差 |
| 实现成本 | 十几行整数运算 | 需 TRNG 初始化与就绪等待 |

预留升级路径：若将来担心同批次 UID 分布有规律，可让主机每轮用 TRNG 生成"盐"随广播下发，从机算 `hash(UQID, salt)`——真随机的均匀性 + 主机握盐可复现。30 台规模不需要。

## 6. 报文格式定义（完整规范）

通用约定：
- 串口 8N1，波特率与常规通信一致（默认 9600bps）；CRC16-Modbus（多项式 0xA001，初值 0xFFFF），**低字节在前**。
- 帧内多字节数据一律大端（高字节在前）；帧间静默 ≥3.5 字符（9600bps 下约 4ms）。
- 多字节数值均为大端（Modbus 寄存器惯例）。

### ① 收集命令（主机 → 总线，广播，功能码 0x06，共 8 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 0x00 | 广播地址 |
| 1 | 0x06 | 写单寄存器 |
| 2~3 | 0x27 0x13 | 命令寄存器 0x2713 |
| 4 | 0xA5 | 魔术字 |
| 5 | round | 轮次号 0~255 循环 |
| 6~7 | CRC16 | 低字节在前 |

示例（round=0）：`00 06 27 13 A5 00 08 3A`；round=1：`00 06 27 13 A5 01 C9 FA`

从机不立即应答；应在 slot 到点后发 ② 帧。

### ② UID 上报帧（从机 → 主机，分时主动发，共 19 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 0x00 | 协议帧标记（广播地址，正常从机永不以 0 回应） |
| 1 | 0x03 | 读寄存器响应形态 |
| 2 | 0x0E | byteCount=14（7 个寄存器） |
| 3~6 | UQID0 | 4 字节大端 |
| 7~10 | UQID1 | 4 字节大端 |
| 11~14 | UQID2 | 4 字节大端 |
| 15~16 | 当前ID | 16 位大端 |
| 17~18 | CRC16 | 低字节在前 |

示例（UID=11223344-55667788-99AABBCC，当前 ID=1）：
`00 03 0E 11 22 33 44 55 66 77 88 99 AA BB CC 00 01 2D F0`

从机延时 = `hash(UQID, round) % 128` × 25ms（自收到①帧的 3.5 字符静默结束起计）。撞车帧叠加乱码，主机 CRC 丢弃。

### ③ 绑定命令（主机 → 总线，广播，功能码 0x10，共 25 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 0x00 | 广播地址 |
| 1 | 0x10 | 写多寄存器 |
| 2~3 | 0x27 0x13 | 起始寄存器 0x2713 |
| 4~5 | 0x00 0x08 | 寄存器数 8 |
| 6 | 0x10 | byteCount=16 |
| 7~8 | 0xA5 0x5A | 魔术字 |
| 9~20 | UID(12B) | UQID0/UQID1/UQID2 各 4 字节大端 |
| 21~22 | 新ID | 16 位大端 |
| 23~24 | CRC16 | 低字节在前 |

示例（给 UID=11223344-55667788-99AABBCC 分配 ID=5）：
`00 10 27 13 00 08 10 A5 5A 11 22 33 44 55 66 77 88 99 AA BB CC 00 05 F0 82`

三重识别（广播地址 + 0x2713 + 魔术字）→ 走分配专用分支，不进入常规 Param_WriteByReg。UID 匹配者执行写入；不匹配者（含其他已分配设备）静默。

### ④ 绑定应答（从机 → 主机，以新 ID 发，标准 0x10 响应，共 8 字节）

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 新ID | **应答地址 = 刚分配的新 ID**（主机由此确认绑定成功） |
| 1 | 0x10 | 功能码回显 |
| 2~3 | 0x27 0x13 | 起始寄存器回显 |
| 4~5 | 0x00 0x08 | 寄存器数回显 |
| 6~7 | CRC16 | 低字节在前 |

示例（新 ID=5）：`05 10 27 13 00 08 3B 3A`

时序：从机写 node_id → Param_Save（Flash 几十 ms）→ 发应答；主机应答超时 ≥300ms。

### ⑤ 验证读取（绑定完成后，主机用新 ID 单播，标准 0x03）

寄存器 0x2741~0x2746（只读，新增）：UQID0/UQID1/UQID2 各拆 2 个 16 位寄存器（大端），共 96 位。紧跟故障状态 0x2740，避开所有已定义地址。主机回读与清点清单比对。

### 流程级时序

- ① 广播后主机静默收听 128 × 25ms = 3.2s（一轮）；每轮结束 round+1 重播，直到连续 1~2 轮无新 UID（封顶 6 轮）。
- ③ 逐台发送，收到 ④（新 ID 应答）再发下一台；30 台约 10s。
- 清点/分配期间主机暂停常规轮询（心跳等）。

### 与严格 Modbus RTU 的偏差（需在协议文档中向客户声明）

- ② 帧是从机**主动上报**（addr=0x00）：标准从机不应答广播、不主动发帧；本协议借用 0x03 响应形态 + 0x00 地址作为私有扩展，帧结构/CRC 与 Modbus 完全兼容，仅语义扩展。
- ④ 帧是对广播 ③ 的应答：标准规定广播不应答；本协议在分配专用分支内应答（地址=新 ID），不影响常规分支行为。

## 8. 设计决策记录

| 决策点 | 结论 | 理由 |
|---|---|---|
| 自动分配 ID | 放弃 | 从机间无通信路径，且客户要自行分配 |
| 清点参与者 | 所有从机（含已分配） | 全网清单、审计冲突、ID 乱总线自愈 |
| slot 来源 | UID 哈希 + round 换盐 | 物理唯一种子、可复现、无故障模式 |
| TRNG | 不用（预留盐升级路径） | 统计保证弱于物理保证；退化输出反而全撞 |
| slot 数 | 128 × 25ms | 30 台 2~3 轮收敛，单轮 3.2s |
| 上报帧 addr | 0x00 | Modbus 广播地址，天然标记协议帧 |
| 未分配判定 | 不需要显式判定 | 清点阶段全员参与，绑定阶段 UID 匹配才执行 |
| UID 验证 | 新增 0x2741~0x2746 回读 | 防止 ID 写歪碰巧读回一致 |
